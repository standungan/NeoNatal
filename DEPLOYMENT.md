# Deployment — VPS

Goal: backend + web dashboard running on your VPS, reachable from home at
`http://<vps-ip>`. Plain HTTP, no domain, no TLS. The Flutter app is not part of
this — it ships as an APK.

```
                          ┌─────────── VPS ───────────┐
Home browser ──:80──▶     │  web (Next.js)            │
                          │    └─▶ backend (FastAPI)  │
Home browser ──:8000──▶   │          └─▶ db (Postgres)│
  (only for /docs)        └───────────────────────────┘
```

Three containers. Postgres is never published — only the other containers can
reach it. The dashboard talks to the backend over the internal compose network,
so `http://backend:8000` never leaves the box and never reaches your browser.

> **This is a testing posture, not a production one.** Over plain HTTP the login
> JWT travels in cleartext. Fine for a portfolio demo you're poking at from home;
> not fine for real patient data. See [Adding HTTPS later](#adding-https-later).

## 1. Prepare the VPS

SSH in, then install Docker:

```bash
curl -fsSL https://get.docker.com | sh
```

Open the two ports. **If your VPS is on AWS / Oracle / GCP / Azure, you must
also open them in the cloud console's security group or firewall rules** — the
host firewall alone is not enough, and this is the single most common reason a
deploy looks dead from home:

```bash
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 8000/tcp
sudo ufw enable
```

**If the VPS has 1 GB RAM or less, add swap before building.** The Next.js build
is the memory-hungry step and gets OOM-killed without it — the symptom is a
build that dies with no useful error:

```bash
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

## 2. Clone and configure

```bash
git clone https://github.com/standungan/NeoNatal.git
cd NeoNatal
cp .env.example .env
openssl rand -hex 32          # copy the output
nano .env
```

Four values must change:

| Key | Set it to |
|---|---|
| `VPS_IP` | your server's public IP |
| `POSTGRES_PASSWORD` | anything long — it never leaves the container network |
| `SECRET_KEY` | the `openssl rand -hex 32` output |
| `LEGACY_SENSOR_INGEST` | **`true`**, if your rigs run the current firmware — see below |

`LEGACY_SENSOR_INGEST` ships as `false` because `/api/sensors` authenticates
nobody: anything that can reach the port can write readings. But the firmware in
`hardware/allsensors/allsensors.ino` posts to exactly that route, so leaving it
`false` means every rig gets a 404 it has no way to report — the only symptom is
a chart that never moves, with a dashboard that looks perfectly healthy beside
it. Set it `true` and keep the API port off the public internet, or move the
rigs to `/api/v1/telemetry` (step 6) and leave it `false`.

Leave `COOKIE_SECURE=false`. Over plain HTTP a `secure` cookie is silently
dropped by the browser, so login would appear to succeed and then bounce you
back to `/login`.

## 3. Build and start

```bash
docker compose up -d --build
```

First run takes a few minutes — it builds two images, pulls Postgres, then
creates the schema and loads demo data. Watch it settle:

```bash
docker compose ps          # all three running, db healthy
docker compose logs -f     # Ctrl-C to stop tailing
```

### How the database gets built (worth knowing)

On its **first** boot — and only then, while the data volume is still empty —
Postgres runs `backend/database/schema.sql` followed by `seed_data.sql` from
`/docker-entrypoint-initdb.d`. That is where your tables and demo data come
from.

It does **not** come from Alembic, and that is deliberate. The migration chain
cannot build a database from scratch: revision `a7821a4243e6` ("initial schema")
was autogenerated against a database that already existed, so it contains only
`DROP INDEX` statements — there is no `CREATE TABLE` for the ten core tables
anywhere in the chain. Run `alembic upgrade head` on an empty database and it
dies on its first statement. `schema.sql` is the real source of truth.

So the backend container stamps Alembic at head on first start rather than
upgrading to it, then upgrades normally on every start after. Migrations you add
from here on work as expected.

You can watch it happen the first time the backend starts:

```
no alembic_version -> schema came from schema.sql; stamping head
INFO  [alembic.runtime.migration] Running stamp_revision  -> e8c4b2f91d37
```

### What has actually been run (2026-09-04)

This file used to describe a stack nobody had brought up. It has now been
exercised end to end on a Windows workstation with Docker Desktop:

- both images build, including the Next.js production build in `web/Dockerfile`
- `db` reaches `healthy` before the backend starts, so the init scripts finish
  first and the backend never sees a half-built schema
- the stamp-then-upgrade above fires as written on an empty volume
- `backend/tests/smoke_check.py` passes **39/39** against the containers
- login through the dashboard's BFF works, and the BFF reaches the backend over
  the compose network and returns all 9 seeded incubators

Two things remain unproven: `docker-compose.tls.yml` (it needs a real domain, so
Let's Encrypt has never been exercised), and this stack on Linux — the rehearsal
above ran on Docker Desktop's WSL2 VM, which is Linux, but not the VPS's distro.

### Rehearsing on a workstation first

Worth doing before touching the server. It is the same two commands, with one
change: if you already run the backend and Next dev server natively, give the
containers different ports in `.env` so the two stacks do not mask each other.

```bash
WEB_PORT=8080
API_PORT=8001
VPS_IP=localhost
```

Dashboard then lands on `http://localhost:8080`, API docs on
`http://localhost:8001/docs`. Note which is which: `WEB_PORT` is the dashboard a
human opens, `API_PORT` is the API the Flutter app and the sensor rigs talk to.
Those two audiences never share a port — see step 6. Generate `SECRET_KEY` and `POSTGRES_PASSWORD` for
this too — a local rehearsal is not a reason to paste in the compromised key
(see step 2).

### One command that checks the whole backend

Clicking around proves the happy path. This proves every module and every RBAC
negative, in about ten seconds, from inside the container — no ports, no
tunnelling, no editing the script (its `BASE` is `localhost:8000`, which *inside*
the backend container is the app itself):

```bash
docker compose exec -T backend python tests/smoke_check.py
```

Expect `39/39 passed`. Anything less names the endpoint that broke. Run it after
every deploy; it is the fastest way to tell "the server is fine, my browser
isn't" from the reverse.

## 6. Point the devices at the server

**Do not skip this.** Both clients have the old address compiled in. Neither
fails loudly — the dashboard keeps working, so it is easy to believe the deploy
succeeded while every device is quietly talking to a machine that no longer
answers.

### The Flutter app

> **Use `API_PORT`, never `WEB_PORT`.** `API_BASE` is the FastAPI origin — the app
> appends `/api/v1/…` itself. Pointing it at the dashboard port looks like it
> works, because `POST /api/v1/auth/login` is unauthenticated and the BFF proxies
> it happily (HTTP 200). Every screen *after* login then fails with
> `403 {"detail":"Not authenticated"}`, because the BFF authenticates from the
> httpOnly `nc_token` cookie and ignores the `Authorization: Bearer` header the
> app actually sends. The symptom reads as a broken token, not a wrong port, so
> it is an expensive hour to debug. In a default deploy that means **`:8000`**,
> not `:80`.

`API_BASE` is baked in **at build time**, not read at runtime, so an installed
APK cannot be repointed — it must be rebuilt and reinstalled:

```bash
cd frontend
flutter build apk --split-per-abi --release   --dart-define=API_BASE=http://<server-ip>:8000
```

Install `build/app/outputs/flutter-apk/app-arm64-v8a-release.apk` (about 19 MB;
the fat APK is 55 MB and holds three architectures you do not need).

Three things that will bite:

- **Flutter is the only client CORS applies to.** The dashboard reaches the API
  server-side over the compose network, so it never triggers CORS at all. The app
  calls FastAPI directly from the device, so `ALLOWED_ORIGINS` must contain the
  address you compiled in — compose builds it from `VPS_IP`, so setting that
  correctly in `.env` covers it. Get it wrong and every request fails with a
  generic connection error that looks exactly like a dead server.
- **Cleartext HTTP is permitted deliberately.** Android 9+ blocks it by default;
  the app ships `res/xml/network_security_config.xml` to allow it, because the
  backend is plain HTTP. Without that the app installs, runs, and fails every
  request with `CLEARTEXT communication not permitted`.
- **minSdk is 24**, so Android 7.0 or newer. Older tablets will not install it.

### The sensor rigs (ESP8266)

The active sketch is `hardware/allsensors/allsensors.ino`. Its configuration is
**hardcoded in the sketch itself**, lines 128-141 — it does *not* `#include
"secrets.h"`, whatever the presence of `secrets.example.h` suggests (that belongs
to `old_allsensors.ino`). Editing `secrets.h` alone changes nothing.

Reflash each rig with:

| Line | What to change |
|---|---|
| `INCUBATOR_ID` | `"inc1"`, `"inc7"`, … — must match an existing `incubator_no` |
| `WIFI_SSID` / `WIFI_PASSWORD` | the ward network |
| `SERVER_URL` | `http://<server-ip>:8000/api/sensors` |
| `STATIC_SUBNET` / `STATIC_IP_LAST` | must match the new network, or set `USE_STATIC_IP 0` for DHCP |

That endpoint is the **legacy ingest route**, and it is disabled by default. With
`LEGACY_SENSOR_INGEST` unset the rigs get:

```json
{"detail":"Legacy sensor ingest is disabled. Use POST /api/v1/telemetry with X-Device-Key."}
```

— an HTTP 404 the firmware cannot report, so the only symptom is a dashboard
that never updates. Set `LEGACY_SENSOR_INGEST=true` in `.env` and
`docker compose up -d backend`, then confirm a rig-shaped payload is accepted:

```bash
curl -X POST http://<server-ip>:8000/api/sensors -H "Content-Type: application/json"   -d '{"incubator_id":"inc1","sensors":{"heart_rate":138,"spo2":97,"ds18b20_temp":36.5,"dht22_temp":33.2,"dht22_humidity":60}}'
```

`{"ok":true,"stored":true,...}` means it is live. Read
[.env.example](.env.example) before enabling it — that route authenticates
nobody, so anything able to reach the port can write readings. The durable fix is
reflashing to the authenticated path (`POST /api/v1/telemetry` with an
`X-Device-Key` header), which `old_allsensors.ino` already implements.

### Registering a device is separate from data arriving

Telemetry on the legacy route stores readings with `device_id` NULL, so an
incubator can stream live while its **Perangkat IoT** card still reads
"Mengirim tanpa terdaftar". To bind a device, an **admin** opens the incubator
and clicks **Pasang Perangkat**. That is what populates online status, last-seen
and sender IP; the chart fills either way.

## Troubleshooting

**Login succeeds then bounces back to `/login`.** `COOKIE_SECURE` is `true` over
HTTP. Set it to `false` in `.env`, then `docker compose up -d web`.

**Nothing loads from home, but `curl localhost` works on the VPS.** Cloud
provider firewall. Check the security group / network rules in the provider
console, not just `ufw status`.

**`port is already allocated` on :80.** Something else is bound — often a
preinstalled Apache or nginx. `sudo ss -tlnp | grep :80`, then
`sudo systemctl disable --now apache2` (or set `WEB_PORT=8080` in `.env`).

**Build dies with no error, or "killed".** Out of memory during `next build`.
Add swap (step 1).

**Dashboard loads but every panel is empty.** The BFF hop is failing:
`docker compose logs backend web`. Usually the backend is unhealthy — check it
reached Postgres.

**`backend` restarts in a loop, logs show `relation "..." does not exist` or an
Alembic error.** The database was created without the init scripts — most often
because a `pgdata` volume already existed from an earlier run, so Postgres
skipped `/docker-entrypoint-initdb.d` entirely. Those scripts run only against
an empty data directory. Wipe and redo:

```bash
docker compose down -v        # deletes the database
docker compose up -d --build
```

**Login page works but there are no users.** Same cause as above — the schema
loaded but the seed didn't, or the volume predates the seed mount. Reload it
with the `psql` command in step 4.

**Dashboard is fine, but no sensor data arrives.** In order of likelihood:
`LEGACY_SENSOR_INGEST` is not `true` (the rigs get a 404 they cannot report —
`curl` the endpoint per step 6 to confirm); the rig's `SERVER_URL` still points
at the old machine; or its `INCUBATOR_ID` names an `incubator_no` that does not
exist on this server, which answers `404 Inkubator '...' tidak dikenal`. Check
what is actually arriving with `docker compose logs -f backend`.

**The Flutter app cannot reach the server, but the dashboard can.** The app is
the only client that goes to FastAPI directly, so it is the only one CORS and
cleartext rules apply to. Either `API_BASE` was compiled with the old address
(rebuild — it cannot be changed after install), or `VPS_IP` in `.env` does not
match it so `ALLOWED_ORIGINS` excludes it. Both surface as a generic connection
error indistinguishable from a dead backend.

**An incubator's chart updates but its device card says no device.** Working as
designed — the legacy route stores readings with no device attached. An admin
must click **Pasang Perangkat** on that incubator. See step 6.

**`docker compose exec db psql ...` says role does not exist.** The `pgdata`
volume was created with different credentials on an earlier run. Wipe and redo:
`docker compose down -v` (**deletes all data**), then `up -d --build`.

## Day-to-day

```bash
docker compose logs -f backend        # tail one service
docker compose restart backend
docker compose down                   # stop (keeps data)
docker compose down -v                # stop AND delete the database

# Deploy an update
git pull && docker compose up -d --build

# Back up the database
set -a; . ./.env; set +a
docker compose exec -T db pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB" \
  | gzip > "backup-$(date +%F).sql.gz"

# Back up uploaded photos (they live in a named volume, not the image)
docker run --rm -v neonatal_uploads:/data -v "$PWD:/out" alpine \
  tar czf "/out/uploads-$(date +%F).tar.gz" -C /data .
```

## Security

Things that are fine for a home-testing deploy and **not** fine beyond it:

- **Traffic is unencrypted.** The JWT is in cleartext on every request.
- **Port 8000 is open to the internet.** It's there for `/docs` and `/health`
  while you bring the box up. The dashboard does not need it — close it with
  `sudo ufw delete allow 8000/tcp` and drop the `ports:` block from the
  `backend` service once you're done poking around.
- **The old `SECRET_KEY` is burned.** `backend/.env` sits in the public
  `neonatal-backend` repo's git history. Never reuse that key; generate a fresh
  one as in step 2. Purging it from history (`git filter-repo` + force-push) is
  worth doing if that repo stays public.
- **The backend image runs as root**, there's no rate limit on
  `/api/v1/auth/login`, and `backend/tests/` is empty.

## Adding HTTPS later

> **Untested.** Everything above the line has been run; this has not — it needs a
> real domain before Let's Encrypt can be exercised at all. Expect to debug it on
> the day, and use `STAGING=1` for the first attempt so a failed run does not burn
> Let's Encrypt's rate limit for that domain.

Once you point a domain at the VPS, [docker-compose.tls.yml](docker-compose.tls.yml)
adds nginx + Let's Encrypt on top of the same stack. Its header has the exact
steps; the short version is: two DNS A records (`app.` and `api.`), edit `.env`,
`export COMPOSE_FILE=docker-compose.yml:docker-compose.tls.yml`, then
`./deploy/init-letsencrypt.sh`.

The API gets its **own subdomain** rather than a `/api/` path on the dashboard
host. That isn't stylistic: the dashboard's BFF already owns `/api/*` on its
origin — the Next route handlers there read the httpOnly `nc_token` cookie and
reissue each call to FastAPI with a `Bearer` header. Mounting FastAPI under
`/api/` on the same host would shadow those handlers, the cookie would never be
exchanged, and every dashboard request would 401 in a way that looks like a
backend fault. Full reasoning in
[deploy/nginx/templates/default.conf.template](deploy/nginx/templates/default.conf.template).
